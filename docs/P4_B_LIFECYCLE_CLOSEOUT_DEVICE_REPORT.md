## 4. Durable session-receipt semantics: policy and observation

| Receipt state | What it warrants | What it **does not** warrant |
| --- | --- | --- |
| **`RUNNING`** | A `RUNNING` generation was durably published at or before the emulation run-start boundary; an interrupted process may leave it behind. | Does not prove a frame ran, that the process is still alive, that unsaved progress is durable, or that exact-frame replay exists. In this test it intentionally survived force-stop byte-for-byte. |
| **`PAUSED`** | Successful stop/save/pause boundary was durably recorded. Also an acceptable truthful *last-known* state after normal Android task removal without guaranteed `onDestroy`. | Does not prove a later shutdown/close completed. Do not fabricate `CLOSED` based on app process absence. |
| **`CLOSED`** | Explicitly completed safe stop/save, unload/shutdown and successful `CLOSED` receipt publication (when that path was executed). | Does not mean every prior instance ended cleanly without evidence, nor supply an exact-frame restore. |
| **`UNKNOWN`** | No valid matching receipt could be established (missing, invalid, conflicting generations or other corruption). Preserve any valid backup and surface uncertainty. | Not a synonym for safe close, crash, or empty native save. Do not overwrite the only good data on this basis. |

Persistent receipt truth is **separate** from Android process status and real native-save payload validation. On cold reselect, validate cartridge SRAM/EEPROM independently; a last `RUNNING` receipt indicates an interrupted/unresolved boundary but does not block using an independently valid durable native save in a fresh process. A normal task-removal `PAUSED` is not a completed `CLOSED`, per explicit mastermind decision. Supported save-state semantics remain separate from native cartridge saves. A dedicated explicit **Exit Game** UI can be planned later, but was **not implemented here**.

## 6. LFC-03 design investigation and smallest safe deterministic test proposal — NOT EXECUTED

Observed implementation:

- `AndroidManifest.xml` declares both `MainActivity` and `DsActivity` with `configChanges="orientation|screenSize|keyboardHidden"`; each `onCreate` calls `setRequestedOrientation(PORTRAIT)`. Consequently, a user rotation gesture is **not** a valid deterministic recreation trigger.
- `MainActivity`'s GBA `SurfaceView` calls `NativeCore.setSurface(surface)` on `surfaceCreated`/`surfaceChanged` and `NativeCore.setSurface(null)` on `surfaceDestroyed`, guarded by a current host token. `plump_host.cpp` protects `ANativeWindow` replacement/painting with a mutex, releases old window references, and logs real posted/rejected/nonblack frames and window errors.
- `DsActivity` separately attaches/detaches top and lower `SurfaceView`s to `NativeDs.topSurface`/`bottomSurface`; lower destruction also releases stylus contact. The native DS adapter locks window replacement; stale session/run callbacks are fenced by `EmulatorSessionOwner` tokens. Both Activities `onPause` attempt durable pause, and `onDestroy` attempts `closeHost` and shutdown. There is no user-verified exact-frame checkpoint or retained URI grant to auto-reopen after recreation.

**Proposed single deterministic test, requiring separate mastermind permission** (no implementation/action under the current authorization):

1. Preserve a **new independent read-only baseline** and launch a **licensed disposable GBA SRAM fixture** on the existing compatible debug build; obtain owner's agreement to potential fixture interruption. Use a purpose-built **test-only Android instrumentation APK** (requires explicit approval to build/install), or an equivalently authorized narrowly scoped test mechanism. Do not change global Android settings or install a modified production APK merely to trigger rotation.
2. Register a test-only Activity lifecycle monitor (record both old/new Java instance identities, `onPause`, `onStop`, **`onDestroy`**, **`onCreate`**, `onStart`, `onResume`) and an additional test-only `SurfaceHolder.Callback` on the real GBA `SurfaceView` to record **`surfaceDestroyed` and `surfaceCreated`**, with valid surface observations. Capture Plump-only logs, PID, worker/resource counts where available, native render stats, and both PLSV/receipt generations before any trigger.
3. Invoke **one** deterministic `ActivityScenario.recreate()` from the instrumentation test thread (not the Android UI thread), targeting the live test Activity **only after approval**; do not simulate rotation or trust Activity foreground/background alone. Assert distinct Activity instance identities, complete old destruction/new creation and actual SurfaceView destruction/recreation, and retained Android process identity. If any callback/host retirement is unresolved, stop; never force a second recreation to hide the failure.
4. Expect the new Activity to **request manual ROM re-selection**, not exact-frame revival. Owner reselects the disposable fixture; verify real SRAM byte-restoration, real frames, physical controls/audio, single current host/worker pair, no duplicate native window owners or renderer errors, valid receipt transitions and all protected save payload hashes.
5. Capture independent final private checksum inventories and exit history, distinguishing successful Activity destruction/creation **from** actual `SurfaceView` callbacks. If the Android surface callbacks are not observed, classify the surface-recreation criterion **INCONCLUSIVE**, regardless of a new Activity instance. Separate DS two-surface and true GPU context-loss stress remain additional tests by future authorization.

This is a **proposal only**. It is not evidence of an LFC-03 pass, and it changes neither installed v8 nor phone settings now. The later LFC-04 work requires a truthful cold-start Resume/Library UX and appropriate unsupported exact-frame messaging; LFC-05 depends on implementing actual permitted reset/menu/cheat/screenshot actions and testing their failure paths without save mutation. No UI or engine architectural decision is silently made here.

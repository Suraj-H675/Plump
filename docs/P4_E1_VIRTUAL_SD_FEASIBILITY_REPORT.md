# Plump P4-E1 — Pinned melonDS virtual-SD feasibility and isolation audit

**Date:** 2026-11-17
**Baseline:** `main` at `ecb40835953cba6906b28ec44d07200b92198d8b` (P4-D4 host accepted).
**Recommendation: PARTIAL / NO-GO for production writable virtual SD.** The exact pinned melonDS DS Linux core accepts an already-formatted **128 MiB FAT16** virtual-SD image, boots two licensed DS homebrew ROMs using different disposable storage roots, and reopens the same FAT image in another process. This is **not** proof that a game performed DLDI `fopen`/`fwrite`/`fclose`/`fread`. The indispensable genuine game-level writer fixture could not be compiled with the available local toolchain. Additional **reproduced safety defects** mean simply enabling virtual SD is unacceptable: the core's *read-only option still changes image bytes*, an unmount-free process exit leaves FAT allocation inconsistency, and a corrupt image can be accepted as a running game while an incompatible `.idx` is created. No E2 integration is authorized by this report.

## 3. Exact bounded pinned-core experiment and measured inventory

New **host-only** reproducible diagnostic files: `tests/roms/verify-p4-e1-virtual-sd.py` and `scripts/test-p4-e1-bounded-host.sh`. Python calls the actual pinned Libretro API and supplies experiment-only homebrew options, never the Android JNI frontend. It validates both ROM hashes, core ELF SHA, confined ignored `app/build` paths, preexisting **exact 134,217,728-byte** FAT image, and Linux `RLIMIT_FSIZE=160 MiB` per file; it also runs under a timeout. Shell uses `truncate -s 134217728` and `mkfs.fat -F 16 -n PLE1TEST` on **new disposable** images, uses sparse copies, retains an immutable source, and only runs `fsck.fat -nv` (read-only, **no repairs**). It never permits the core to create the default 4 GiB image. Images, `.idx`, ROMs, snapshots and host logs remain Git-ignored.

Run from repository root:

```bash
PYTHONDONTWRITEBYTECODE=1 bash scripts/test-p4-e1-bounded-host.sh \
  > app/build/p4-e1/bounded-host-final.log 2>&1

# Inspect the final independent disposable run without modifying the image:
fsck.fat -nv "app/build/p4-e1-acceptance-qdEWnNMm/canonical/save/melonDS DS/dldi_sd_card.bin"
```

The second command names the **specific** inspected final run and is not a cleanup command. The shell prints its exact newly created root; generated names and whole-image SHA-256 vary because the core injects a boot ROM and writes FAT directory metadata. Final run: `app/build/p4-e1-acceptance-qdEWnNMm/`; source log `app/build/p4-e1/bounded-host-final.log`. All executable scenarios completed with exit **0**, meaning diagnostic execution/classification completed, **not** writable-SD acceptance.

**Disk bounds:** each working file's *logical* size was 134,217,728 bytes; typical allocated size **282,624–544,768 bytes**. All working cases stayed under the 160 MiB per-file size limit and 32 MiB actual-block budget; no uncontrolled full-size copy or 4 GiB creation. A corrupt image's autogenerated `.idx` referencing 512 MiB illustrates why **validating logical image size and `.idx` together** is mandatory. Sparse footprint is a *Linux-host filesystem observation*, not an Android storage/performance estimate; versioning and backup may require full copies depending on filesystem support.

## 4. Why the essential real-game persistence gate remains blocked

The pinned SDK has a **CC0 reference implementation** `examples/filesystem/save_data/source/main.c`. It genuinely calls `fatInitDefault()`, obtains the executable path, opens a `.sav`, reads/writes button counters, closes the file and prints results; this is the correct *starting point* for a deterministic Plump-specific fixture with explicit `magic`, ROM tag, monotonically increasing sequence, checksum, verify-after-close, and cold-restart result printed or rendered on the DS screens.

At this E1 execution the official BlocksDS SDK **source** was cached and pinned, but `/opt/blocksds/core`, `arm-none-eabi-gcc` and Wonderful Toolchain were not installed; the Docker CLI was present but its daemon/socket was **inactive**, and noninteractive `sudo` required a password. The earlier P3 official image digest `skylyrac/blocksds@sha256:c5f19b95d9c2f312e6a68ea244d2ed5120203b4b82af9785937a349096f8e5e4` could therefore not be used to compile a new NDS fixture. Official BlocksDS supported routes are its pinned Docker SDK or Wonderful/BlocksDS ARM toolchain, **not** using the Android NDK C compiler as a drop-in substitute for libnds/libfat. No repetitive SDK installation, Docker daemon reconfiguration, custom FAT implementation or unreviewed binary substitution was attempted.

**Consequently unavailable:** an original compiled E1 ROM; genuine emulated `fopen`→write→close→reopen→checksum pass; independently cold-restored file record; repeated in-game writes; game-level two-ROM/branch separation; DLDI sector-write injection at a true game write; no-space failure from an in-game write; and a coherent historical machine+FAT state rollback test. It would be false to label any of these PASS because the core modified an image while booting. Existing D1/D4 cartridge SRAM/EEPROM evidence does not substitute for it.

## 5. Fail-closed E2 proposal — **not authorized for implementation**

**Smallest gating next action: make a real game-level BlocksDS fixture executable, then repeat E1.** Use the already pinned official SDK image *when a working toolchain environment is separately available* (or an independently pinned equivalent build environment). Adapt only the CC0 `save_data` sample. Each ROM must display its immutable test identity, old sequence, new sequence, checksum and failure; use two different compiled ROM identities; perform `fopen`/`fwrite`/`fflush`/`fclose` and `fopen`/`fread` from emulated ARM9; verify in-game before unload, after cold restart, after repeated writes and in separate canonical/historical save roots. Generate only ignored `.nds`/test images. **If this genuine proof fails, writable SD remains unsupported.**

If that gate passes, the minimal *proposed* E2 architecture is:

1. **Per-game/branch storage identity:** one exclusive active working tree for `(DS, exact ROM SHA-256, branch UUID or canonical)` containing FAT `.bin`, actual `.idx` if present, required sidecars and a versioned ownership record. Do not share `nds-core-data/melonDS DS/` across games; no symlink/path traversal; DSi/NAND virtual storage separately unsupported; never mix cartridge PLSV with this image.
2. **Immutable source, writable copy:** retain the last verified complete image-plus-sidecar generation independently and use a private writable copy for the live core. The core's reported `melonds_homebrew_readonly` **cannot** protect originals. On missing/corrupt/oversized/unexpected FAT or conflicting `.idx`, block launch or enter explicit recovery; **never** offer the bad copy to an engine that may silently autoformat it. Prevent a 4 GiB creation with exact bounded preformatted size and free-space preflight; initially 128 MiB is *boot-feasible only*, not yet game-write-compatible.
3. **Exclusive quiescent commit:** stop frames under the existing session owner, unload/close the *actual* native FAT image, capture any failure/close status with a **narrow core/frontend health adapter if required**, and independently verify FAT, file sizes and image+sidecar SHA-256. Fsync all files and the directory before publishing a complete immutable generation. A checksum alone does not prove replay; require genuine cold game-level reopen/readback on a disposable generation to establish compatibility. Never claim that a 30-second cartridge PLSV flush commits FAT.
4. **Multi-file atomicity and rollback:** stage immutable image+`.idx`+manifest together with size/schema/core/ROM/branch identity, fsync/readback; atomically publish a complete candidate directory and then an independent durable active-generation pointer. Maintain previous good generation and uncertain recovery classification. The working copy may be dirty after crash; quarantine rather than auto-mount and **never** delete a prior good image based on a new failed copy. No implicit branch promotion or merging of diverged filesystems/RTC.
5. **Real failure proofs:** repeat with the working DLDI writer at image, `.idx`, sector write, close, native file sync and pointer publication boundaries; test missing/read-only/corrupt image, incorrect index size, disk-full simulation without exhausting the host, folder-sync accidentally enabled, game switch, process hard-stop and correctly paired machine+image generations. **No historical DS homebrew state loading** until paired machine+native image and cold replay are proven. Measure actual copy-on-write/copy costs, size ceiling and storage quota on Android only after further approval.

**Potential upstream adaptation:** even if a frontend-only working-copy/checkpoint scheme avoids changing the pinned core, robust E2 needs observable native FAT mount/format/error/close status and a way to prohibit implicit destructive reformat. The discovered `FF_WriteStorage` read-only bypass merits a small upstream fix or equivalent strict working-copy isolation. **Any core source change/rebuild/revision change requires its own evidence-backed mastermind approval.** Do not rebuild or modify the pinned core during E1.
